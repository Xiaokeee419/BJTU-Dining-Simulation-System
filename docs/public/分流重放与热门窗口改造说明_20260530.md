# 分流重放与热门窗口改造说明

日期：2026-05-30  
开发分支：`feature/cohort-replay-diversion-tuning`

## 目标

本次改造同时解决两个问题：

1. `baseline` 和 `compare` 必须基于同一批用户重放，保证对比只反映分流策略本身的影响。
2. 未分流仿真需要更容易形成“热门窗口更拥挤、冷门窗口更空闲”的状态，分流建议则改为按相对压力均衡，不再依赖“源窗口必须拥挤、目标窗口必须不拥挤”的硬阈值。

## 已实施的修改

### 1. 后端仿真改为同 cohort 重放

文件：

- `backend/src/main/java/com/bjtu/dining/taska/service/SimulationService.java`

改动：

- baseline 运行时只抽样一次用户 cohort，并按 `runId` 保存在内存中。
- compare 运行时不再重新采样，而是直接复用 `baseRunId` 对应的 cohort，从 `minute=0` 重新跑完整轮仿真。
- compare 和 baseline 共用同一批人的：
  - 到达时间
  - 预算区间
  - 等待容忍度
  - 口味偏好
  - 热门偏好
  - 排队厌恶程度
  - 接受分流倾向

效果：

- 分流前后对比变成真正的 A/B replay。
- 不再受二次采样波动干扰。

### 2. 未分流选窗逻辑改为“热门偏置 + 延迟厌队 + 概率抽样”

文件：

- `backend/src/main/java/com/bjtu/dining/taska/service/SimulationService.java`

改动：

- 用户选窗口时，提高了窗口热度和餐厅吸引力的影响。
- 等待惩罚改成分段函数，在等待尚未明显超过容忍阈值前，用户仍更愿意去热门窗口。
- 由“始终选择最高分窗口”改成“按窗口得分做加权抽样”，但抽样种子已经固化在 cohort 中，因此 replay 仍可复现。
- 菜品选择也改成基于固定种子的加权选择，避免 compare 过程中因为随机序列漂移带来额外噪声。

效果：

- baseline 更容易出现头部窗口聚集。
- 同样人数下，更容易看到部分窗口拥挤、部分窗口空闲。

### 3. 分流建议改为按相对压力均衡

文件：

- `backend/src/main/java/com/bjtu/dining/recommendation/service/RecommendationService.java`

改动：

- 所有营业窗口先计算压力分数，压力分数综合考虑：
  - 等待时间
  - 队列长度
  - 服务率
  - 当前拥挤等级
- 源窗口改为从“压力显著高于平均值”的窗口中选取。
- 目标窗口改为从“营业且压力低于源窗口”的窗口中选取。
- 目标窗口不再要求必须处于 `IDLE/NORMAL`。
- 同一个目标窗口允许承接多个源窗口，但会扣减可承接余量，避免过度分流。
- 建议分流人数改为根据：
  - 压力差
  - 队列差
  - 目标承接余量
  - 源窗口超额队列
  综合估算。

效果：

- 分流建议不再只在极端拥挤场景下出现。
- 分流逻辑更符合“从相对更忙转向相对更闲”。

### 4. 分流作用方式

文件：

- `backend/src/main/java/com/bjtu/dining/taska/service/SimulationService.java`

改动：

- 对已经在队列中的人：在分流起始分钟按聚合方式转移一部分队列。
- 对分流起始分钟之后新到达的人：按其固定的接受倾向概率决定是否遵循推荐改道。
- 改道判定不仅看接受率，还会结合当前时刻的实时压力差和等待改善。

效果：

- compare 不会变成“所有人都强制听从分流”的理想化结果。
- 结果更接近“建议引导 + 部分接受”的真实场景。

### 5. 前端人数范围做最小调整

文件：

- `frontend/src/components/ScenarioPanel.vue`

改动：

- 虚拟就餐人数滑块范围从 `100-2000` 调整为 `300-1800`。
- 对 `EXTREME` / `IDLE` 场景的提示阈值同步调整。

原因：

- 过低人数通常难以稳定展示分流效果。
- 过高人数容易把所有窗口一起推高，不利于观察“相对均衡”。

## 前后端接口边界

本次改造没有改变现有前端依赖的接口形状：

- `POST /api/v1/simulations/run`
- `POST /api/v1/strategies/diversion-comparison`
- `GET /api/v1/simulations/{runId}`

因此：

- 前端页面结构无需重写。
- 现有对比页仍然直接使用 `baselineRun`、`compareRun`、`baseMetrics`、`compareMetrics`、`comparison`。

## 主要影响文件

- `backend/src/main/java/com/bjtu/dining/taska/service/SimulationService.java`
- `backend/src/main/java/com/bjtu/dining/recommendation/service/RecommendationService.java`
- `frontend/src/components/ScenarioPanel.vue`

## 验证建议

建议重点验证以下路径：

1. 运行一轮 baseline，确认当前分钟能形成更明显的热门窗口聚集。
2. 保存 baseline 后运行分流对比，确认 `compareRun` 可正常生成。
3. 对比 `maxQueueLength`、`busyWindowCount`、`extremeWindowCount`、`unservedUserCount` 是否出现下降。
4. 切换不同分钟点，确认分流建议会随着窗口压力变化而变化。
