# 新增优化方案、分工与接口规范

版本：v0.3

日期：2026/5/25

适用范围：本文件用于说明当前项目在已有 MVP 基础上的新增优化内容、A/B/C 成员分工、接口字段约定和联调流程。该文件作为 `新版分工方案.md` 与 `接口规范.md` 的补充说明，后续确认后可再同步合并到正式接口规范。

---

## 1. 新增优化目标

当前项目已经完成“配置参数、运行仿真、展示排队状态、生成推荐、场景对比”的基本闭环。下一阶段优化目标是让系统更像一个完整的校园就餐仿真与决策支持工具，而不是单页演示。

新增优化内容包括：

1. 可视化展示就餐数据统计信息。
2. 前端页面改为带导航的多页面结构，而不是所有模块集中展示。
3. 增加推荐功能前后的就餐情况数据对比。
4. 进一步优化推荐算法，使推荐结果更符合不同用户画像。
5. 优化人流数据生成逻辑，使早餐、午餐、晚餐曲线更贴近真实就餐规律。
6. 重新制定仿真分流逻辑，使分流建议可结构化、可解释，并能够影响后续仿真结果。

本阶段仍然保持原有系统定位：

```text
成员 A：仿真数据生成与效果评估
成员 B：分流策略与推荐算法
成员 C：仿真控制台与可视化展示
```

## 2. 关键业务调整

### 2.1 午餐错峰规则

午餐高峰需要从单峰模型调整为双峰模型。

约定如下：

| 项目 | 时间 | 仿真分钟 |
| --- | --- | --- |
| 午餐仿真开始 | 11:30 | 0 |
| 第一批下课 | 12:00 | 30 |
| 第二批下课 | 12:20 | 50 |

午餐人流曲线应体现：

1. 12:00 第一批下课后形成第一波到达高峰。
2. 12:20 第二批下课后形成第二波到达高峰。
3. 两个峰之间允许有短暂回落，但不应完全降为低谷。
4. 高峰到达时间可考虑 3 到 8 分钟步行延迟，因此实际窗口排队峰值可略晚于下课时间。
5. `randomSeed` 相同时，生成结果应尽量保持可复现。

建议调整 `data/task-a/arrival_rules.csv` 中 LUNCH 规则，例如：

```text
LUNCH,11:30,12:00|12:20,30|50|38,0.48|0.42|0.10,7|8|14,午餐人流由 12:00 和 12:20 两批错峰下课驱动，形成双峰。
```

说明：

1. `30` 和 `50` 是两批下课核心峰。
2. `38` 可作为两峰之间和步行延迟导致的缓冲峰。
3. 实现时可根据算法需要调整权重和标准差，但最终展示应能看出双峰。

### 2.2 早餐和晚餐规则

早餐：

1. 单峰为主。
2. 仿真开始时间建议保持 07:00。
3. 主峰约 07:35 左右，对应 08:00 上课前集中就餐。
4. 峰后下降较快。

晚餐：

1. 可使用宽峰或轻微双峰。
2. 整体曲线应比午餐更平缓。
3. 可体现 18:30 下课后形成主峰，并允许一部分学生晚些就餐。

## 3. 新增功能说明

### 3.1 就餐数据统计可视化

目标：让用户不仅能看到某个时间点的排队状态，还能看到完整就餐时段的统计趋势。

新增展示内容：

1. 总就餐人数趋势。
2. 各餐厅客流趋势。
3. 平均等待时间趋势。
4. 最大排队长度趋势。
5. 餐厅客流占比。
6. 窗口拥挤等级分布。
7. Top N 拥挤窗口。
8. 已服务人数、未服务人数、服务完成率。

前端可以优先基于已有 `timePoints` 和 `metrics` 计算这些统计数据，不强制新增后端接口。

### 3.2 前端导航式页面

当前前端以一个 `SimulationDashboard` 页面集中展示所有模块。新增优化后，建议拆成带导航的多页面结构。

推荐页面：

| 路由 | 页面名称 | 主要内容 |
| --- | --- | --- |
| `/dashboard` | 数据总览 | 核心指标、总趋势、客流概览 |
| `/simulation` | 仿真配置 | 用户画像、场景参数、运行仿真 |
| `/queue` | 排队态势 | 时间轴、餐厅列表、窗口排队表 |
| `/recommendation` | 推荐分流 | 推荐餐厅、窗口、菜品和分流建议 |
| `/comparison` | 效果对比 | 推荐前后、分流前后指标对比 |

视觉要求：

1. 保持当前项目已有风格，不重新设计成完全不同的后台系统。
2. 继续使用当前酒红主色、白色面板、8px 圆角、Element Plus 控件和 ECharts 图表。
3. 顶部保留项目品牌区，可在品牌区下方增加横向导航。
4. 页面主体继续复用 `.panel`、`.panel-header`、`.panel-body` 等现有样式。
5. 不使用夸张大屏风、营销页风格或过度装饰背景。

### 3.3 推荐前后就餐情况对比

推荐前后对比不应只展示推荐结果文字，而要展示应用推荐或分流策略后的仿真指标变化。

推荐流程：

```text
C 运行基准仿真
-> A 返回 baselineRunId、timePoints、metrics
-> C 调用 B 生成推荐与分流计划
-> B 返回 recommendationResult 和 diversionPlan
-> C 将 diversionPlan 传给 A 再运行一次策略仿真
-> A 返回 afterRunId、timePoints、metrics
-> C 调用 B 的策略对比接口
-> B 返回指标差值和结论
-> C 展示推荐前后变化
```

对比指标：

1. 平均等待时间变化。
2. 最大等待时间变化。
3. 最大排队长度变化。
4. 拥挤窗口数量变化。
5. 极端拥挤窗口数量变化。
6. 已服务人数变化。
7. 未服务人数变化。
8. 餐厅客流分布变化。

### 3.4 推荐算法优化

推荐算法继续采用规则加权，不强制引入机器学习模型。

推荐评分应区分用户类型：

| 用户类型 | 推荐偏好 |
| --- | --- |
| `STUDENT` | 口味、等待、预算均衡 |
| `HURRY` | 更重视等待时间和队列长度 |
| `BUDGET_SENSITIVE` | 更重视预算匹配 |
| `FACULTY` | 可更重视稳定性、等待时间和舒适度 |
| `VISITOR` | 可更重视热门度和易理解推荐理由 |

推荐分数建议拆分为：

```text
总分 = 口味匹配分
     + 预算匹配分
     + 等待时间分
     + 拥挤度分
     + 热门度分
     + 餐厅吸引力分
     - 关闭或不可用惩罚
```

推荐理由应尽量包含：

1. 匹配了哪些偏好。
2. 预计等待多久。
3. 是否低于用户等待容忍度。
4. 是否符合预算。
5. 当前拥挤等级。
6. 相比高拥挤窗口的优势。

### 3.5 分流逻辑优化

分流逻辑需要从文本建议升级为结构化计划。

分流分为三步：

1. 识别拥挤来源窗口。
2. 寻找可承接目标窗口。
3. 计算建议分流人数、接受率和预计改善效果。

来源窗口筛选条件：

1. 窗口状态为 `OPEN`。
2. 拥挤度为 `BUSY` 或 `EXTREME`。
3. 等待时间超过目标拥挤等级对应阈值。
4. 排队人数足够产生可分流空间。

目标窗口筛选条件：

1. 窗口状态为 `OPEN`。
2. 当前等待时间低于来源窗口。
3. 当前拥挤度不高于目标拥挤等级。
4. 服务能力可以承接额外用户。
5. 标签和来源窗口尽量相近。

接受率影响因素：

1. 等待时间节省越多，接受率越高。
2. 标签相似度越高，接受率越高。
3. `HURRY` 用户接受率更高。
4. 预算敏感用户对价格差异更敏感。
5. 分流距离或餐厅变化越大，接受率可适当降低。

## 5. 新增接口与字段约定

### 5.1 场景配置新增字段

接口：

```text
POST /api/v1/simulations/run
```

归属：成员 A

用途：运行基准仿真或应用推荐/分流策略后的仿真。

在原有 `scenario` 基础上建议新增：

```json
{
  "strategyMode": "BASELINE",
  "diversionPlan": [],
  "recommendationAdoptionRate": 0.35,
  "diversionAdoptionRate": 0.25
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `strategyMode` | String | 否 | 仿真策略模式，默认 `BASELINE` |
| `diversionPlan` | Array | 否 | B 生成的结构化分流计划 |
| `recommendationAdoptionRate` | Number | 否 | 推荐采纳率，范围 0 到 1 |
| `diversionAdoptionRate` | Number | 否 | 分流采纳率，范围 0 到 1 |

`strategyMode` 枚举：

| 值 | 含义 |
| --- | --- |
| `BASELINE` | 原始自然就餐仿真 |
| `RECOMMENDED` | 应用推荐引导后的仿真 |
| `DIVERSION` | 应用分流计划后的仿真 |

兼容要求：

1. 如果前端不传新增字段，后端必须按 `BASELINE` 处理。
2. 旧版请求仍应可用。
3. 新增字段应写入返回结果的 `scenario` 中，方便 C 展示和对比。

### 5.2 分流计划结构

接口：

```text
POST /api/v1/recommendations/diversion
```

归属：成员 B

用途：根据某一次仿真结果生成结构化分流计划。

请求示例：

```json
{
  "runId": 10001,
  "minute": 30,
  "targetCrowdLevel": "NORMAL",
  "profile": {
    "userType": "STUDENT",
    "tasteTags": ["辣味", "米饭"],
    "budgetMin": 10,
    "budgetMax": 22,
    "waitingToleranceMinutes": 10
  }
}
```

说明：

1. `profile` 可选；如果传入，B 可根据用户类型调整接受率。
2. `targetCrowdLevel` 表示希望分流后目标窗口不超过的拥挤等级。

响应 `data` 示例：

```json
{
  "runId": 10001,
  "minute": 30,
  "suggestions": [
    {
      "fromRestaurantId": 1,
      "fromWindowId": 101,
      "toRestaurantId": 2,
      "toWindowId": 205,
      "suggestedUserCount": 18,
      "acceptanceRate": 0.35,
      "estimatedAcceptedCount": 6,
      "estimatedWaitReduction": 7,
      "tagSimilarity": 0.72,
      "reason": "目标窗口等待更短，口味相近，预计减少 7 分钟等待"
    }
  ],
  "reason": "已生成 1 条分流建议，目标拥挤度不高于 NORMAL。"
}
```

新增字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `acceptanceRate` | Number | 预计接受分流比例，范围 0 到 1 |
| `estimatedAcceptedCount` | Integer | 预计实际接受分流人数 |
| `estimatedWaitReduction` | Number | 预计等待时间减少分钟数 |
| `tagSimilarity` | Number | 来源和目标窗口标签相似度，范围 0 到 1 |

兼容要求：

1. 旧字段 `fromRestaurantId`、`fromWindowId`、`toRestaurantId`、`toWindowId`、`suggestedUserCount`、`reason` 保留。
2. C 展示时优先展示结构化字段；如果字段不存在，则回退展示 `reason`。

### 5.4 策略对比接口增强

接口：

```text
POST /api/v1/strategies/compare
```

归属：成员 B

用途：比较基准仿真和策略仿真的效果差异。

请求示例：

```json
{
  "baseRunId": 10001,
  "compareRunId": 10002,
  "compareType": "RECOMMENDATION_AFTER"
}
```

`compareType` 枚举：

| 值 | 含义 |
| --- | --- |
| `SCENARIO` | 普通场景对比 |
| `RECOMMENDATION_AFTER` | 推荐前后对比 |
| `DIVERSION_AFTER` | 分流前后对比 |

响应 `data` 建议增强：

```json
{
  "baseRunId": 10001,
  "compareRunId": 10002,
  "avgWaitDelta": -2.4,
  "maxQueueDelta": -8,
  "busyWindowCountDelta": -3,
  "extremeWindowCountDelta": -1,
  "servedUserCountDelta": 24,
  "unservedUserCountDelta": -24,
  "conclusion": "应用分流策略后平均等待时间降低 2.4 分钟，最大排队减少 8 人，整体分流效果较好。"
}
```

新增字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `compareType` | String | 对比类型，可选 |
| `unservedUserCountDelta` | Integer | 未服务人数变化 |

兼容要求：

1. 不传 `compareType` 时按普通场景对比处理。
2. C 判断指标好坏时，等待、排队、拥挤、未服务人数下降为正向；已服务人数上升为正向。

```json
  "servedUserCount": 742,
  "unservedUserCount": 58,
  "serviceCompletionRate": 0.9275,
  "peakArrivalMinute": 30,
  "peakArrivalCount": 95
}
```

新增字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `serviceCompletionRate` | Number | 服务完成率 |
| `peakArrivalMinute` | Integer | 到达人数最多的时间点 |
| `peakArrivalCount` | Integer | 峰值到达人数 |

说明：

1. 如果 A 暂不返回新增字段，C 可先在前端根据 `timePoints` 计算统计数据。
2. 为了更准确展示到达峰值，后续可在 `SimulationTimePoint` 中补充 `arrivedCount`。

### 5.6 时间点数据增强建议

现有 `SimulationTimePoint`：

```json
{
  "minute": 30,
  "restaurants": []
}
```

建议增强为：

```json
{
  "minute": 30,
  "clockTime": "12:00",
  "arrivedCount": 95,
  "servedCount": 62,
  "restaurants": []
}
```

新增字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `clockTime` | String | 当前仿真分钟对应真实时间，例如 `12:00` |
| `arrivedCount` | Integer | 当前时间片新增到达人数 |
| `servedCount` | Integer | 当前时间片服务完成人数 |

兼容要求：

1. 新字段可选。
2. C 若未拿到 `clockTime`，可继续显示 `第 N 分钟`。
3. C 若未拿到 `arrivedCount`，可先用餐厅人数变化估算趋势，但正式展示建议由 A 返回。

## 7. 联调流程

### 7.1 第一阶段：文档和字段确认

1. 三人确认本文件中的新增字段。
2. 如果新增字段影响正式接口，更新 `docs/public/接口规范.md`。
3. 如果新增字段影响 A 数据结构，更新 `docs/A/任务A仿真数据结构设计.md`。
4. 如果新增字段影响 B 返回结构，更新 `docs/B/B模块开发TODO.md`。

### 7.2 第二阶段：并行开发

成员 A：

1. 实现到达曲线优化。
2. 支持午餐双峰。
3. 支持策略模式和分流计划输入。

成员 B：

1. 实现推荐评分 v2。
2. 实现结构化分流计划。
3. 增强策略对比结论。

成员 C：

1. 实现前端导航。
2. 拆分页面。
3. 新增统计图表和推荐前后对比页面。
4. 在不影响 A、B 成员接口联调和共同开发边界的前提下，为了页面美观、展示协调和操作流程清晰，可以适当调整页面布局、页面命名、导航顺序和跳转关系。

### 7.3 第三阶段：真实链路联调

联调顺序：

1. C 调 A：运行 `BASELINE` 仿真。
2. C 调 B：基于 `baselineRunId` 生成推荐和分流计划。
3. C 调 A：携带 `diversionPlan` 运行 `DIVERSION` 仿真。
4. C 调 B：比较 `baselineRunId` 和 `afterRunId`。
5. C 展示推荐前后对比结果。

### 7.4 最小验收场景

建议最终演示使用：

```text
用户画像：学生，偏辣/米饭，预算 10-22 元，等待容忍 10 分钟
场景：工作日午餐高峰
时间规则：11:30 开始，12:00 第一批下课，12:20 第二批下课
仿真人数：800 到 1200
步长：5 分钟
```

演示步骤：

1. 打开数据总览页，展示当前暂无运行或最近一次运行概览。
2. 进入仿真配置页，选择午餐高峰场景。
3. 运行基准仿真。
4. 进入排队态势页，播放时间轴，观察 12:00 和 12:20 两个高峰。
5. 进入推荐分流页，生成推荐和分流计划。
6. 应用分流计划，再运行一次策略仿真。
7. 进入效果对比页，展示推荐前后指标变化。

## 9. 风险与注意事项

1. 午餐双峰不要只在前端图表上模拟，真实后端仿真也必须体现。
2. 前端拆页面时不要丢失全局状态，当前 runId、推荐结果、对比结果应由 Pinia 统一管理。
3. B 的分流计划不要只返回文字，必须保留结构化字段，便于 A 应用策略和 C 展示。
4. A 应用分流计划时不能把所有人都转移到同一个目标窗口，需要考虑接受率和目标窗口承载上限。
5. 推荐前后对比应基于两次真实仿真结果，而不是 C 前端自行修改数字。
6. 如果新增字段暂时无法一次性完成，应保证旧接口仍然能支撑当前 MVP 演示。
