# 本次修改汇总

日期：2026-05-30  
当前分支：`feature/cohort-replay-diversion-tuning`

## 1. 本次修改目标

本次改动围绕“未分流 baseline”和“分流 compare”的可信度、展示效果和可执行性展开，目标有五项：

1. 让 `baseline` 和 `compare` 基于同一批用户重放，避免二次抽样造成结果波动。
2. 让未分流仿真更容易形成“热门窗口更拥挤、部分窗口更空闲”的状态。
3. 让分流建议从“硬阈值拥挤判断”改为“相对压力均衡”。
4. 压缩“有拥挤窗口但完全不给出分流建议”的常见空结果场景。
5. 让前端趋势图直接展示分流最关心的“局部压力变化”，而不是全局总量。

## 2. 实际修改内容

### 2.1 后端仿真重构

文件：

- `backend/src/main/java/com/bjtu/dining/taska/service/SimulationService.java`

主要改动：

- baseline 运行时只抽样一次用户 cohort，并以 `runId` 关联缓存。
- compare 运行时复用 `baseRunId` 对应的 cohort，从 `minute=0` 重新完整跑一遍仿真。
- cohort 中固定保存：
  - 到达时间
  - 预算范围
  - 等待容忍度
  - 口味偏好
  - 热门偏好
  - 排队厌恶程度
  - 接受分流倾向
  - 决策采样种子
- 窗口选择逻辑从“选最高分窗口”改为“带固定种子的加权抽样”。
- 等待惩罚改为分段函数，前期更弱，后期快速增强。
- 菜品选择也改为固定种子的加权选择，避免 replay 过程中随机序列偏移。
- 分流生效后：
  - 已在队列中的人按聚合方式做部分转移
  - 新到达的人按接受概率决定是否遵循分流建议

结果：

- compare 真正变成“同一批人群重放对比”。
- baseline 更容易形成热点聚集，而不是过早被排队惩罚自动均衡。

### 2.2 分流建议逻辑改为相对压力均衡

文件：

- `backend/src/main/java/com/bjtu/dining/recommendation/service/RecommendationService.java`

主要改动：

- 不再要求“源窗口必须高于目标拥挤等级阈值”。
- 不再要求“目标窗口必须处于 `IDLE/NORMAL`”。
- 对所有营业窗口计算压力分数，综合考虑：
  - 等待时间
  - 队列长度
  - 服务率
  - 当前拥挤等级
- 源窗口从压力明显高于平均值的窗口中选取。
- 目标窗口从压力低于源窗口且仍有承接余量的窗口中选取。
- 建议分流人数按以下因素综合估算：
  - 源目标压力差
  - 队列差
  - 目标承接余量
  - 源窗口超额队列
- 同一个目标窗口允许承接多个源窗口，但会扣减剩余容量，避免过量灌入。

结果：

- 分流建议更贴近“从相对更忙转向相对更闲”。
- 即使不是极端拥挤窗口，也可能被识别为可优化对象。

### 2.3 针对“无建议”场景增加三层兜底匹配

文件：

- `backend/src/main/java/com/bjtu/dining/recommendation/service/RecommendationService.java`
- `frontend/src/stores/simulationStore.js`

问题来源：

- 原始改法虽然去掉了“目标窗口必须空闲”的硬限制，但仍要求目标窗口显著更轻且有足够容量。
- 当前端把 `targetCrowdLevel` 压成 `NORMAL` 时，目标窗口容量估算也会变得更保守。
- 结果就是：某些场景明明有拥挤窗口，但没有任何窗口同时满足“更轻 + 容量足 + 压力差显著”，于是直接返回空建议。

本次补充改动：

- 新增 `selectTargetCandidate(...)`，目标窗口匹配改成三层：
  - 严格匹配：优先找明显更轻、容量充足的窗口
  - 放宽匹配：放宽压力差和容量上限，给出次优但可执行的目标窗口
  - 应急匹配：若仍无结果，则允许非常小规模的试探性转移，避免直接空建议
- 新增 `strictPressureBuffer(...)`，不同拥挤等级下使用不同的压力差门槛。
- 新增 `relaxedMaxQueueForLevel(...)`，放宽模式下允许目标窗口承接更多队列。
- 新增 `emergencyRemainingCapacity(...)`，应急模式下按极小承接额度估算。
- 新增 `fallbackTargetScore(...)`，在兜底阶段按压力差、等待差、队列差和剩余容量综合排序。
- 前端 `resolveDiversionTargetLevel(...)` 不再一律把目标等级压成 `NORMAL`，而是把当前场景真实等级继续传给后端。

结果：

- 只要系统里存在可操作的相对转移空间，就尽量给出建议，而不是直接空结果。
- 即使没有特别空闲的窗口，也会优先返回“小规模、次优但可执行”的分流方案。

### 2.4 第二轮强化：让 baseline 更挤、让 compare 更明显

文件：

- `backend/src/main/java/com/bjtu/dining/taska/service/SimulationService.java`
- `backend/src/main/java/com/bjtu/dining/recommendation/service/RecommendationService.java`

强化方向：

- baseline 侧进一步放大热门窗口聚集效果。
- compare 侧进一步提高已在队列中的转移量和新到达用户的改道概率。

具体改动：

- 提高 `WINDOW_SELECTION_TEMPERATURE`，让热门窗口分布更集中。
- 收紧 `BUSY/EXTREME` 的到达扩散系数，让高峰更集中。
- 提高用户的 `popularityBias` 上限，降低预算因素在选窗中的影响。
- 进一步减弱选窗前期的等待惩罚，让热门窗口在变得“明显不合理”之前持续吸人。
- 提高已在队列中的 `desiredTransfer` 估算，增加已排队用户在分流开始分钟的转移量。
- 放宽新到达用户改道时的压力差门槛，并提高 `effectiveAcceptanceRate`。
- 提高 `suggestedUserCount(...)` 和 `acceptanceRate(...)` 的上限与系数，让推荐策略本身更有力度。

结果：

- baseline 的最大窗口队列和忙碌窗口数量更容易抬高。
- compare 的忙碌窗口数量和头部窗口排队总量更容易出现可见下降。

### 2.5 前端趋势图改造

文件：

- `frontend/src/components/DiversionComparisonPanel.vue`
- `frontend/src/utils/simulationStats.js`

问题来源：

- 原趋势图展示的是“总排队人数”和“总负载人数”。
- 但分流本质上是在调整窗口之间的分布，不会明显改变系统总人数。
- 所以很多时候前后曲线看起来重合，即使局部最拥挤窗口已经被缓解。

本次改动：

- 新增局部压力统计函数：
  - `maxWindowQueueLength(point)`
  - `topWindowQueueSum(point, limit)`
- 趋势图从“全局总量”改为“局部压力走势”：
  - 未分流最大窗口队列
  - 分流后最大窗口队列
  - 未分流头部窗口总排队
  - 分流后头部窗口总排队
- 趋势图说明文案同步更新，明确它是在看“局部压力是否被打散”。

结果：

- 页面上更容易一眼看出分流是否在峰值附近把局部拥挤压下去。
- 不再因为全局总量天然接近而误判“分流完全没效果”。

### 2.6 前端人数范围调整

文件：

- `frontend/src/components/ScenarioPanel.vue`

主要改动：

- 虚拟就餐人数滑块范围从 `100-2000` 调整为 `300-1800`。
- `EXTREME` 和 `IDLE` 的提示阈值同步收紧。

原因：

- 太低的人数通常不容易稳定展示分流效果。
- 太高的人数容易把所有窗口一起推高，不利于观察“相对均衡”。

## 5. 验证结果

已完成的验证：

- 后端编译通过：`mvn -DskipTests compile`
- 前端构建通过：`npm run build`
- 真实后端接口验证通过：
  - baseline 可正常运行
  - diversion comparison 可正常运行
  - 同一个 `baseRunId` 连续运行两次 compare，建议数量和关键指标变化一致

针对兜底匹配的验证：

- 在 `BUSY/LUNCH` 场景下，对 `300/400/500/600/800/1000/1200` 人数做了真实接口验证。
- 使用 `POST /api/v1/recommendations/diversion` 时，这些人数区间均能生成 `8` 条分流建议。
- 说明“有拥挤窗口但完全不给建议”的常见空结果场景已被明显压缩。

针对第二轮强化后的验证：

- 在 `BUSY/LUNCH`、`virtualUserCount=1200` 的场景下：
  - `compare` 生成 `8` 条建议
  - `busyWindowCountDelta = -6`
  - `avgWaitDelta = -0.2`
  - 在峰值分钟 `35`：
    - baseline 最大窗口队列 `20`
    - compare 最大窗口队列 `18`
    - baseline 头部 5 个窗口总排队 `96`
    - compare 头部 5 个窗口总排队 `84`
    - baseline 忙碌窗口数 `7`
    - compare 忙碌窗口数 `0`
- 在 `800/1000/1200` 三组人数验证中：
  - `800` 人：`maxQueueDelta = -1`
  - `1000` 人：`busyWindowDelta = -2`
  - `1200` 人：`busyWindowDelta = -6`

结论：

- baseline 的局部拥挤更明显了。
- compare 不一定总能显著降低“全局总排队人数”，但已经能更稳定地降低“头部窗口压力”和“忙碌窗口数量”。
- 前端趋势图改成局部压力指标后，这种改善能在页面上更直接地体现出来。
